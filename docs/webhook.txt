可以。你现在已经有 Webhook 基础能力，下一步最合理的不是继续给 Webhook 页面塞复选框，而是抽象成一个完整的 **Event Delivery / Notification Center（事件通知中心）**。

我下面按“现有 Webhook + Lark + Spug Push”来设计。这里的 Spug 我按 **Spug 推送助手/HTTP 推送渠道**理解；Spug 官方本身也支持通过 URL 做多渠道推送，而 Spug DevOps 的部署 Webhook 是另外一种“触发部署”的用途，不应和通知渠道混在一起。Spug 目前也原生支持飞书等消息推送场景。

# Event Delivery / Notification Center 设计

## 1. 模块定位

把当前已有的：

```text
Webhook
```

升级为：

```text
Notifications
├── Channels
├── Event Subscriptions
├── Templates
├── Delivery Logs
└── Settings
```

核心思想：

```text
业务模块
    ↓
Domain Event
    ↓
Event Bus
    ↓
Notification Engine
    ↓
Subscription Matcher
    ↓
Template Renderer
    ↓
Delivery Queue
    ↓
Channel Adapter
    ├── Generic Webhook
    ├── Lark
    └── Spug
```

业务模块完全不知道：

```text
Lark
Spug
Webhook URL
```

只负责：

```text
emit("post.published", payload)
```

通知模块自己决定是否发送、发送到哪里。

---

# 2. 不要把“事件”和“渠道”绑定死

错误架构：

```text
post.publish
→ sendLark()

comment.created
→ sendWebhook()
```

应该：

```text
post.published
        ↓
Notification Engine
        ↓
Subscriptions
        ↓
┌──────────────┬─────────────┬─────────────┐
│ Lark         │ Spug        │ Webhook     │
└──────────────┴─────────────┴─────────────┘
```

因此同一个事件可以：

```text
Post Published
├── Lark ✓
├── Spug ✗
└── Webhook ✓
```

另一个事件：

```text
AI Report Failed
├── Lark ✓
├── Spug ✓
└── Webhook ✗
```

# 11. 核心：Event Registry

系统所有可通知事件，必须注册到统一：

```text
Event Registry
```

而不是后台自己硬编码复选框。

例如：

```ts
eventRegistry.register({
  name: "post.published",
  module: "content",
  label: "Post Published",
  description: "Triggered when a post is published",
  severity: "info"
})
```

模块关闭：

```text
Store disabled
```

那么 Store Events 自动从 UI 消失。

# 32. Event Payload 标准化

所有通知事件统一：

```ts
interface NotificationEvent {
  id: string

  name: string

  module: string

  severity:
    | "info"
    | "warning"
    | "error"
    | "critical"

  occurredAt: string

  actor?: {
    type: string
    id?: string
    name?: string
  }

  entity?: {
    type: string
    id: string
    title?: string
    adminUrl?: string
    publicUrl?: string
  }

  data: Record<string, unknown>
}
```

例如：

```text
event:
post.published

entity:
Post #123

data:
title
slug
category
publishedAt
```

# 35. Webhook Signature

Generic Webhook 建议支持：

```text

```

请求头：

```text

X-Webhook-Signature
```


# 36. SSRF 防护

因为管理员可以配置：

```text
Webhook URL
Lark URL
Spug URL
```

服务端请求必须防 SSRF。

至少：

```text
禁止 localhost
禁止 127.0.0.0/8
禁止 ::1
禁止私网 IP
禁止 metadata endpoint
DNS resolve 后再次验证
限制 redirect
限制协议 http/https
```

如果你的产品允许 self-host 用户向内网 Webhook 推送，则：

```text
Allow Private Network
```

必须做成显式高级设置，默认关闭。

# 44. Outbox Pattern

这部分我强烈建议。

业务事务：

```text
Publish Post
```

不要：

```text
save post
↓
HTTP call Lark
↓
成功才能完成
```

如果 Lark 超时，文章发布不能失败。

应该：

```text
DB Transaction

Post Published
+
Event Outbox Record

COMMIT
```

然后异步：

```text
Notification Worker
↓
read outbox
↓
match subscriptions
↓
deliver
```

# 74. 很重要：双层事件

建议区分：

```text
Domain Event
```

和：

```text
Notification Event
```

例如：

```text
post.view.incremented
```

是 Domain Event。

但：

```text
notifiable = false
```

后台完全看不到。

而：

```text
post.published
```

是：

```text
notifiable = true
```

这样 Event Picker 不会逐渐出现几百个内部技术事件。

# 最终架构

```text
                Application Modules
                         │
      ┌──────────────────┼──────────────────┐
      │                  │                  │
    Posts             Store               AI
      │                  │                  │
      └────────── Domain Events ────────────┘
                         │
                    Event Registry
                         │
                       Outbox
                         │
               Notification Engine
                         │
               Subscription Matcher
                         │
                Template Renderer
                         │
                   Delivery Queue
                         │
          ┌──────────────┼──────────────┐
          │              │              │
        Lark            Spug         Webhook
          │              │              │
       Human          Human        Automation
     Notification     Alert           System
```

这套方案最关键的一点是：**不要再把 Webhook 当成“通知系统本身”，Webhook 只是 Notification Channel 的一个 Provider。**

以后你增加 Telegram、Discord、Email、企业微信，只需要新增：

```text
TelegramChannelAdapter
DiscordChannelAdapter
EmailChannelAdapter
```

Event、Subscription、Template、Retry、Logs、Outbox 全部不需要重做。

另外，Spug 官方当前还支持独立的“部署 Webhook”，用于 Push/Tag 触发部署，并带 Secret Token 校验；如果以后你想让博客后台的某个事件去**触发 Spug 部署/流水线**，我建议另做 `Automation Action`，不要放到现在这个 Notification Channel 里。

这里我尤其建议你把 **Subscription + EventPicker** 作为这次重构的核心，而不是先做模板编辑器。第一阶段把“渠道创建 → 可视化选事件 → Outbox 异步发送 → 失败重试 → 日志”跑通，整个通知基座就已经非常完整了。
