
下面这版可以直接作为你当前 Nuxt 博客/CMS 的 **Settings 模块正式设计稿**。

# Nuxt CMS Settings 模块优化设计

## 1. 设计目标

Settings 不应该是：

```text
key
value
JSON
```

这种开发者配置页。

后台用户看到的应该是：

```text
站点标题
站点描述
网站 Logo
默认语言
评论开关
SEO 设置
AI 模型
邮件配置
存储配置
```

底层仍然可以：

```text
settings
├── key
├── value
├── type
└── group
```

但 UI 层必须是：

> Schema-driven Form

即：

```text
Settings Schema
      ↓
Field Renderer
      ↓
Modern Admin Form
      ↓
Settings Service
      ↓
KV / JSON Storage
```

---

# 2. 核心原则

冻结以下原则：

```text
1. 普通管理员绝不编辑 Key
2. 普通管理员绝不编辑 Raw JSON
3. Settings UI 由 Schema 自动生成
4. 模块自己注册自己的 Settings
5. Settings Core 不知道具体业务模块
6. 支持动态启用/隐藏模块
7. Secrets 单独处理
8. Environment > Database > Default 的来源必须可见
9. 保存必须有 Dirty State
10. 不做“所有设置一个超长页面”
```

# 4. Profile 不放 Settings

你刚刚设计的：

```text
/profile
```

不要放：

```text
Settings → Profile
```

因为 Profile 是内容实体。

应该：

```text
Content
└── Profile
```

或者：

```text
Profile
├── Overview
├── Sections
├── Social Channels
├── Experience
├── Projects
├── Skills
├── Education
├── Certifications
├── Current Focus
└── SEO
```

Settings 只处理：

```text
系统行为
站点行为
模块默认值
基础设施
```

而不是具体内容。

同理：

```text
Slider
Advertising Campaign
Products
AI Reports
Friend Links
```

都不是 Settings Record。

# 7. Dirty Save Bar

只有修改设置以后出现：

```text
┌──────────────────────────────────────────────────┐
│ Unsaved changes                  Discard   Save │
└──────────────────────────────────────────────────┘
```

建议 sticky：

```text
bottom: 16px
```

或者顶部 sticky。

必须支持：

```text
Dirty detection
Unsaved route guard
Discard changes
Save changes
```

用户离开页面时：

```text
You have unsaved changes.
```

---

# 8. 不要每个字段自动保存

尤其：

```text
SMTP
Storage
AI API Key
Security
Payment
```

如果输入一个字符就保存，很危险。

推荐：

```text
Form state
↓
Dirty
↓
Save
↓
Validate
↓
Batch Update
```

---

# 9. 左侧 Navigation

Navigation 不应该写死。

由：

```text
Settings Registry
```

生成。

例如：

```ts
settingsRegistry.register({
  id: "comments",
  group: "publishing",
  label: "Comments",
  icon: MessageSquare,
  order: 20
})
```

如果 Comments 模块未启用：

```text
Comments
```

自动消失。

# 11. Settings Schema

核心结构建议：

```ts
interface SettingDefinition {
  key: string

  group: string
  section?: string

  label: string
  description?: string

  type: SettingFieldType

  defaultValue?: unknown

  required?: boolean

  validation?: unknown

  options?: SettingOption[]

  visibleWhen?: SettingCondition

  disabledWhen?: SettingCondition

  sensitive?: boolean

  restartRequired?: boolean

  source?: "database" | "environment" | "default"
}
```




# 54. Module Settings Contract

建议每个模块：

```ts
interface SettingsContributor {
  namespace: string

  registerSettings(
    registry: SettingsRegistry
  ): void
}
```

例如：

```text
CommentsModule
AdvertisingModule
StoreModule
AIModule
```

启动：

```text
Module Registry
↓
```

# 67. Settings Schema 与数据库分离

这里非常重要：

```text
Schema
```

定义：

```text
有什么设置
是什么类型
默认值
怎么验证
怎么展示
```

数据库：

```text
只存覆盖值
```

例如：

Schema：

```text
comments.enabled default true
```

如果数据库没有记录：

```text
true
```

来自 default。

用户改成 false：

数据库：

```text
comments.enabled = false
```

点击 Reset：

删除 DB override。

重新：

```text
true
```

程序第一次运行即可获得 default。

```text
✓ 保存自动 invalidate

✓ Dark Mode 正常

```

# 82. 最终建议

你当前 Settings 最值得做的不是继续“增加设置项”，而是先把 **Settings Foundation** 做正确。

冻结成：

```text
Schema Registry
+
Visual Settings UI
+
Module Registration
+
Source Resolution
+
Secure Secrets
+
Search
+
Dirty Save
```

然后业务模块只需要：

```text
register settings
```

就自动获得：

```text
UI
Validation
Default
Search
API
Permissions
Cache
```

这会让你以后继续开发 Blog、Store、Advertising、AI、Comments、Payments 时轻松很多。

特别是最新加入的：

```text
Page AI
AI Assistant
Profile
```

应该遵循同一个边界：

```text
Settings
→ 管“系统怎么运行”

Business Module
→ 管“具体内容是什么”
```

这样 Settings 不会最终变成一个什么东西都往里塞的超级页面。

我建议当前实际开发顺序直接按 **S1 → S2 → S3 → S5(AI)**，因为你现在正在继续做 Page AI / AI Assistant；商城、支付、系统级 Provider 可以等核心设置框架稳定以后再逐步注册进去。
