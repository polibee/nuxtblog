# 通用架构设计与开发约束

## 目标

本规范用于 Nuxt CMS、后台管理系统和可扩展业务项目。目标是让模块可替换、数据访问可测试、多语言可维护、权限可验证、异步请求可取消，并让每个功能在合并前有可重复的质量证据。

## 一、统一分层

```text
页面 / 组件
  -> composable / application service
  -> domain service
  -> repository contract
  -> database adapter / external adapter
```

- 页面只处理展示、交互和路由参数，不能直接访问数据库。
- 通用框架不能反向依赖具体业务模块。
- API handler 只负责鉴权、输入校验、调用 service 和映射错误。
- Service 负责业务规则、事务边界、事件和缓存失效。
- Repository 只负责持久化，不承载权限、页面文案或业务流程。
- 外部服务（邮件、Webhook、支付、AI、存储）必须通过 adapter contract 接入。

## 二、模块契约优先

每个业务模块必须先定义以下边界：

1. Entity：领域读取模型，不暴露数据库行结构。
2. CreateInput / UpdateInput：创建和更新分离，清空值使用显式 `null`。
3. Repository interface：稳定的方法名、参数和返回值。
4. Service：事务、业务冲突、事件和缓存策略。
5. API contract：请求、响应、状态码和权限。
6. Resource/UI contract：表格、表单、详情、Action 和翻译 key。
7. Test contract：正常、空值、权限、冲突、并发和错误路径。

数据库实现必须通过 context 注入：

```ts
type DomainRepositoryContext = {
  page: PageRepository
  post: PostRepository
  profile: ProfileRepository
  transaction<T>(work: (ctx: DomainRepositoryContext) => Promise<T>): Promise<T>
}
```

MySQL、PostgreSQL、Supabase 和 memory 只能实现相同 contract，业务层不得判断 dialect。写入 ID、时间、分页和事务结果统一由 adapter 映射。

## 三、路由、Alias 与资源 URL

- Alias 是用户可见资源的稳定标识，不把数据库 ID 当作公开 URL。
- URL 生成集中在 resolver；导航、站点地图、SEO、卡片和重定向必须复用它。
- Alias 修改先写入旧 Alias -> 新 Alias 的 301 记录，再更新主记录，二者必须在同一事务中完成。
- 旧 Alias 不直接删除；重复 Alias 返回 409。
- 站内重定向只允许相对路径，外部 URL 必须显式审查。
- 管理端 URL、API URL 和公开内容 URL 不得混用。

## 四、多语言标准

- 语言包按模块拆分，聚合入口保持稳定。
- UI 文案、错误提示、表单标签、导航标题和后台 Action 不得硬编码。
- 中文是默认语言；英文名称为空时使用 Alias 或系统英文标识。
- 文章标题、摘要和正文按文章自身语言独立维护，不用 Alias 替代文章标题。
- `t(key, params)` 插值、未知 key、locale fallback 和 zh/en key parity 必须有测试。
- 语言切换必须同步 URL、刷新数据请求和页面元信息，不依赖手动刷新。

## 五、权限、错误和安全

- 前端权限只控制体验，服务端每个管理 handler 必须再次检查用户和权限。
- 统一错误语义：401 未登录、403 无权限、422 输入错误、409 业务冲突、503 外部依赖不可用。
- 错误响应返回稳定 code 和安全 message，不泄露 SQL、凭据、路径或堆栈。
- 富文本、图片 Embed、评论、Webhook、AI 和导出统一经过输入上限、超时、速率限制和安全校验。
- 外部 URL 进行协议、主机、解析地址和私网地址校验，不能只检查字符串前缀。
- 金额使用最小货币单位整数和显式货币代码。

## 六、异步、事务和缓存

- 每个异步操作都带 request id 或 generation token。
- 组件卸载、路由离开或输入变化后，旧请求不得更新状态、emit 或覆盖新结果。
- `AbortError` 显式忽略；其他错误必须进入可见错误状态或返回给调用方。
- 事务只由 service/repository context 创建，外部通知不能成为核心 CRUD 成功的必要条件。
- 数据变更必须触发对应缓存失效、模块 refresh 事件和必要的搜索/统计更新。
- 重试使用指数退避、上限、幂等键和可观测状态。

## 七、表单、资源和公共 UI

- 创建与编辑表单都必须真实回显已有值。
- 保存期间禁用重复提交；成功、失败、空状态、加载状态和权限不足都有明确 UI。
- schema 是纯数据描述，渲染器负责布局和控件。
- 资源 Action 必须声明权限并发出 `{resource}:refresh`。
- 公共组件必须考虑 SSR、深链接刷新、键盘操作、移动端和无障碍。
- 文章图片默认限制在内容列宽内，保持比例；大图通过 lightbox 查看，不影响卡片和侧边栏布局。

## 八、测试和提交闸门

每个任务按以下顺序执行：

1. 先写能复现问题的失败测试。
2. 实现最小修改。
3. 运行 focused unit/API 测试。
4. 运行 lint 和 typecheck。
5. 做独立只读代码审查并修复发现项。
6. 准备交付时运行 `npm test -- --run`、`npm run build`。
7. 浏览器、真实数据库、外部 Webhook 等不可用环境必须标记为未验证。

测试必须覆盖：权限边界、输入校验、空值和分页、事务回滚、Alias 301、locale fallback、XSS/SSRF、异步取消和缓存失效。

## 九、Git 与演进纪律

- 开工前执行 `git status --short`，已有修改属于用户，不能重置或覆盖。
- 一个任务只提交自己的文件和精确 hunks；无法安全拆分时生成 patch 并暂停提交。
- 公共接口、持久化格式、路由和架构选择必须补 ADR。
- 删除兼容代码前必须有迁移清单、调用方扫描、回归测试和可恢复方案。
- 文档中的示例代码只能作为设计参考，不能被运行时自动导入。

## 十、模块验收清单

- [ ] contract、service、adapter、API、UI 和权限边界明确。
- [ ] 创建、编辑、删除、空状态、冲突和失败路径可测试。
- [ ] 公开 URL、Alias、locale 和 SEO 使用统一 resolver。
- [ ] 数据库操作只通过 repository/context，事务边界明确。
- [ ] 事件、缓存和外部通知失败不会破坏核心 CRUD。
- [ ] focused tests、lint、typecheck、全量 test/build 的结果已记录。
- [ ] 真实环境验证范围、未验证项和回滚方式已写清楚。
